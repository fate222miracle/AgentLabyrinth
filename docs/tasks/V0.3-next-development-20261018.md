## 2. 开发顺序与交付标准

### A. 下一项直接开发：保存记录的离线记忆诊断

**问题**：网页已能比较阅读次数，但尚未把窗口、容量跳过和最终失败联系成一份可复查材料。已有CLI只固定一题生成两次单Episode，不应再复制一个实验执行器。

实施范围：

1. 提供显式的本地产物审查入口，指定一个保存的Experiment或一对Episode；仅读取文件，不联网、不创建任务、不重新执行模型/工具。
2. 复用现有Artifact/计划来源校验、`content_hash`、上下文配置和成对固定变量规则。指定正式Experiment时按其配对关系读取；指定两份CLI记录时明确标为独立Episode探索，不补造Experiment身份。
3. 从已有`MODEL_REQUESTED.context`列出每次请求的窗口、记忆条数、实际字节、跳过条数与源call_id；从成功工具事件计算阅读/重复。记录模型、任务/工具/Runtime版本、预算、终止、评分和已报告用量。
4. 输出一份带来源ID的阅读报告。没有相关诊断、缺Trace或用量未知时明确缺失；不能把字节当Token，把失败时零读取当效率提升，或把“跳过且失败”直接当作已证实因果关系。
5. CLI原有结果不覆盖，原始Trace不裁剪；输出独立目录，失败也保留诊断。本轮先做CLI和说明，现有Web继续使用已保存数据，不创建新看板/API。

拟复用/阅读：`scripts/episodic_memory_ablation.py`的逐侧报告与读取计数、`application/experiment.py`固定变量校验、`application/checkpoint.py`与Artifact读取、`runtime/context.py`诊断、`flowFrames.documentEvidence`网页口径。优先提取现有必要逻辑，不建通用插件/报告框架；实际改动文件在任务实施前按调用链确定。

验收：正常记录可回溯至原事件；错误ID、错配配置、损坏来源拒绝；无记忆历史与缺诊断保持未知；失败/null/未返回不计读；整个审查过程零Provider/工具调用，原文件哈希不变。用已有Fake产物作确定性检查；既有真实产物若本机缺失，报告缺失而不重跑或补造。

**完成条件**：用户能读完一个报告，回答“哪次请求保留/跳过了什么来源，哪里再次读取了文档，任务是否完成”，同时区分事实和待验证解释。

### B. 随后开发：少量有必要依赖的记忆压力场景

先形成具体任务设计与Proposed ADR，明确新增数据的版本、目录/入口、工具权限、Fake规则、评分与旧历史兼容；负责人确认后才接入正式任务目录。下列是候选问题，不是已实现任务或保证产生收益的样本。

| 候选场景 | 要检验什么 | 设计约束 |
| --- | --- | --- |
| 跨阶段证据复用 | 较早读取的关键事实离开近期窗口后是否仍能正确使用 | 任务本身需要连接早期与后期事实；不人为要求重复查阅或规定固定调用次数 |
| 超大工具返回 | 整条结果超过记忆上限被跳过时，任务能否完成、代价如何变化 | 保留真实完整返回和预算；不截取答案注入，不因记忆失败放宽证据评分 |
| 相似/旧版本干扰资料 | 记住内容是否仍会选错依据 | 生效条件在模型可见资料中明确；先做静态版本差异，不偷加动态世界、时间失效协议或隐藏正确答案 |

起步每种机制一个清晰实例；验证后再决定是否需要独立变体，不机械扩成大数据集。原12题、三个跨文档任务、BFCL和保存版本保持；新增数量以批准的任务设计为准。

对照设计：正式`memory_ablation`固定同N轮、左无记忆/右有记忆。`full`作为另一次显式参照，不混进同一纯记忆成对结果；只改容量的探针另标容量实验，不跨N/M/任务混合历史趋势。先复用已有N1/M8192及256字节边界，按文档实际序列化大小决定是否需要额外容量值。

验收：规则能独立判定答案和已取得证据；Fake只解析公开观察/工具返回，不读goal_conditions或按任务ID给答案；完整上下文下任务有可验证解法；Trace能解释窗口和容量边界。不能为固定“右侧赢”的结果改任务或评分。新增场景最终必须能在API/Web选择、实时演示、只读回读和比较，不停留在测试夹具或脚本。

### C. 小样本真实验证：先补正式入口证据

实际执行前确定本机可用模型和具体任务；本规划不自动发真实请求。

- 第一次只选一个模型、一个已有跨文档任务，使用正式`memory_ablation`保存计划与结果，共两侧Episode；新压力任务后续另行选择，不同一轮把所有候选都跑完。
- 初始候选固定LangGraph/本地工具、N1/M8192，每侧最多10步、配置20000报告Token和300秒，沿用现有预算语义；按需设全局Token准入预算，不把Episode边界控制称为网关实付或严格费用硬上限。
- 运行前冻结模型、温度、Prompt、工具/任务版本、Runtime/恢复策略、Seed及预算。所有结果保留，包括两侧都失败或记忆侧更慢。供应商错误保留部分产物，停止后续新增探索，不自动换模型或挑最好结果；已受理执行遵守现有Job/恢复协议，不在报告脚本私加重试/取消语义。
- 分开报告任务通过、工具调用、成功/重复阅读、输入/输出Token、耗时、跳过记忆及未知用量。保持当前固定左右顺序并说明顺序/模型随机性局限；需要交叉顺序或批量统计时另做设计，不静默改编排。

**完成条件**：获得一份能从新Web结果穿透到真实Trace的正式小样本，或获得明确的网关/模型失败诊断。两者都能结束本次验证；不要求出现预定提升百分比。

### D. 按证据选择下一种机制

| 观察到的主要问题 | 后续动作 |
| --- | --- |
| 记忆被容量整条排除且影响完成 | 先分析实例与可替代工具返回设计，再提一个具体记忆策略ADR；不直接引入向量库/摘要模型 |
| 来源已进入请求，但模型仍反复读取 | 检查来源呈现和决策行为；不能直接归因容量或用硬规则禁止再次读取 |
| 信息齐全但遗漏任务前置/证据子目标 | 优先规划Planning Challenge，比较现有直接行动与显式子目标跟踪；先定义计划状态、辅助调用计费、恢复及单变量对照ADR |
| 主要是限流、断线或输出截断 | 作为Provider/可靠性问题处理，不包装成记忆或规划算法缺陷 |
| 当前机制已经足够完成任务 | 保留当前实现和边界报告，结束记忆切片，不为引进技术而改算法 |

Planning是需求中的下一候选能力，尚未批准具体实现。本次不预建Planner、Reflection、LLM Judge、第二Runtime Adapter、SQLite、跨任务知识库或多Agent模块。多Agent世界/角色与论文阅读继续作为未来参考，进入对应阶段时再形成具体设计。
