# UI信息架构评估与重编排建议

日期：2026-11-02。**状态：评估/候选方案，尚未实施或批准新API/依赖。** 本轮只读检查产品、使用设计技能并记录建议，不改生产UI、不发任务或Judge请求、不提交Git。

## 1. 结论和依据

建议进行页面职责与运行阅读流程的结构性重设计，然后统一视觉。React单页应用可以拥有多个稳定路由；当前问题是多个不同工作目标集中在同一长页面，不能把“换成多个HTML文件”或“多加几个菜单”当成解决方案。

需求V0.6 §17已定义Experiment List/Builder、Experiment Detail、Episode Trace/Replay三个逻辑页面；当前仅通过single/experiment工作区和query参数切换，在一个App中同时承载配置、运行、恢复、历史、评审和分析。已有35项任务、六类对照变量，复杂度超过原双模式长页面。

证据来自：

- 本地实际浏览器读取新建单次、配置展开、已保存Episode、对照配置四种界面；全程未点击运行/恢复/Judge。
- 一条已保存Episode `e762c985…`（有多条真实评审）的1280×720视口DOM量测：文档总高约4578px；草稿栏从385px开始、145px高；指标从547px开始、340px高；Judge区域从903px开始、高约1702px；Trace从2621px开始。该样本说明多条评审会把过程挤到约3.6个视口后，不能外推所有历史页高度都相同。
- 新建页首屏截图中，标题、目录说明、历史ID框和配置摘要占据大量空间，舞台主体落到首屏下缘；新建页文档高约1998px（当前最近记录和场景数量影响高度）。
- 源码核对：App.tsx约3180行，index.css约2629行；App同时拥有路由/历史、实时流、运行配置、结果选择、恢复控制和CSV导出等职责。行数不直接等于质量，但职责集中增加布局修改和导航竞态的维护风险。
- 正常API有meta、单Episode详情/恢复列表/Review、Experiment列表/详情/进度/Job读取；**没有全量Episode分页摘要列表GET**。目前“最近运行”来自localStorage最近五个ID，并非完整数据库浏览器。

## 2. 主要问题

| 优先级 | 观察 | 用户后果 | 优化方向 |
| --- | --- | --- | --- |
| P0 | 配置、正在执行、旧结果、未来草稿共享页面 | 需要不断确认当前在操作什么；折叠只改变可见性，没有稳定工作位置 | 分开新建、运行详情、记录列表；当前运行详情只显示保存配置，重新运行另建草稿 |
| P0 | 多条Judge完整堆在回放前 | Agent过程和最终输出被挤到数屏后，课堂讲述中断 | 运行详情以过程为主；评审独立子视图，默认先展示最新结论摘要，历史评审按需阅读 |
| P1 | UUID读取框、最近记录、恢复列表和实验历史散落 | 查找记录依赖记忆ID，既有成果难浏览 | 独立运行记录与实验列表，按任务/模型/时间/状态查找；ID作为复制和精确查询辅助 |
| P1 | 任务目录、场景预设和配置混合 | 一边浏览长任务说明，一边被大量技术选项打断 | 任务库集中浏览，任务详情完整阅读；“配置运行”只进入草稿，显式开始才POST |
| P1 | 对照页同时提供配置、历史趋势、恢复和结果 | 新建实验与分析结果互相挤占，难聚焦差异 | 实验列表、实验新建、实验详情分开；详情先结论、再任务差异、再钻取Episode |
| P1 | 大页头、重复介绍/摘要、多层相似卡片 | 上下阅读跨度大，重要区域都像同权重模块 | 紧凑应用页头；整页一个主画布，以轻分隔组织内容，减少重复标题和边框 |
| P2 | 中英文术语混用、长字段说明直接占据正常操作区 | 初次使用者读不懂；课堂观众关注技术细节而非任务结果 | 中文目标/行动优先，ID/版本/原始JSON/计价细节按需查看，必要边界提示仍保持可查 |
| P2 | 文档与屏幕存在历史遗留 | 后续协作容易继续按过时假设设计 | UI规范表头仍为1.13/2026-10-26且部分范围表把Planning/Reflection列为未来项；新建加载空态仍出现“从左侧目录”措辞，应随实施统一校准 |

原有狐狸品牌、暖色与文字对比、实际Trace、资料阅读/引用关联、源配置只读、未知费用、键盘焦点及减少动效是应保留的基础。不能以重设计为由削弱可信状态或把真实运行改成完成后动画。

## 3. 推荐页面结构

建议四个一级入口，详情页面归属于相应入口；这是候选信息架构，不是新增管理后台。

| 区域 | 唯一主要工作 | 候选路由 | 主要内容 |
| --- | --- | --- | --- |
| 任务库 | 找到适合演示/实验的任务 | /tasks | 课堂推荐、ToolLab/BFCL来源筛选、能力标签、中文目标；详情显示任务说明/输出要求/工具能力和配置入口 |
| 执行工作台 | 配置并现场观察一次执行 | /workbench | 当前草稿、常用模型/Runtime、按需展开参数；待机说明精简，开始后舞台占主画面 |
| 运行记录 | 找到、解释并复查已有运行 | /runs、/runs/:id | 列表筛选、真实状态/时间/模型/来源、保存结果只读；从实验钻取也使用同一详情组件 |
| 实验中心 | 建立对照并解释变化 | /experiments、/experiments/new、/experiments/:id | 实验列表和已有可比趋势；独立新建配置；详情显示固定条件、差异指标、任务对和下钻 |

主路径：任务库 → 配置草稿 → 显式运行 → 实时运行详情 → 结果/评审。再次运行从保存配置创建独立草稿，不能在历史页顶部持续展示无关“下次运行”配置。

为避免再次挤窄画布，优先评估顶部四区导航；如果采用侧导航，应只放稳定的全局入口并允许在专注运行时收起，不能把整套配置塞回侧栏。服务/模型状态放公共状态入口或轻量工具区；当前没有的探测结果显示未知，不做无后端依据的在线绿灯。

## 4. 运行详情的空间与状态

- 顶部只保留任务中文名、短ID/来源、实际模型/Runtime及真实状态。正常界面不重复完整草稿摘要。
- 内容子视图为“执行过程 / 结果分析 / 模型评审 / 技术记录”；过程默认可见，中央画布加右侧行动/依据Inspector，Inspector只查看当前选择，不重复整份运行。
- 运行中只显示已到达事件、当前调用和实际资料；结束后保持原画布及最终输出，不自动重播或跳走。完成后才提供结果与评审的完整阅读入口。
- Judge从主纵向流移到评审子视图，显示最新结论/理由/引用与规则的分歧；其余评审列表化。新建评审必须显式选模型点击，旧失败和用量未知不变。
- 配置采用短行常用设置、整行高级设置；较长设置可独立编辑页。任务浏览不能把整页拖成长表单；主导航也不通过弹窗完成。
- 1280×720等课堂视口首先能看到主要执行区域与当前行动，不需要滚过历史ID表单、Judge和长说明；窄屏先画布、再当前依据，以可切换Inspector保持阅读顺序。

## 6. 实施顺序与可行性

1. **先做核心线框与状态表**：任务选择、运行中、完成结果、失败/断线、历史回读和实验差异各有明确位置；先确定页面职责，再落颜色/动效。产出能直接审阅的静态或离线原型，不用真实模型支撑布局演示。
2. **先落运行详情切片**：提取公共应用壳、只读来源摘要和运行详情，移动Judge与技术视图，保留实时流及证据组件。随后分离任务库与配置工作台，再迁实验列表/详情。逐个切片验证，避免一次重写全部前端。
3. **补完整记录浏览的真实数据支撑**：任务库可复用meta，实验列表可复用GET /experiments；完整Episode列表需有界分页/过滤/摘要契约和SQLite/旧JSON兼容设计，按项目规则先具体ADR，不承诺纯前端即可完成。不为凑页面增加任务CRUD、账户/权限、自动评审或多Agent菜单。
4. **路由与状态归属**：草稿、运行会话、保存产物、记录筛选分别拥有状态。URL和浏览器前进/后退一致；既有?mode=single、?episode_id和?experiment_id链接继续只读兼容。实时订阅不能因为视图卸载被误认为任务失败；刷新后现无真实SSE重连能力，显示已保存/连接未知，不自动重新POST、恢复或模拟实时。
5. **体验验收再固化**：1440/1280/768/390、640等效窄视口、键盘和动态减少动效；刷新/快速导航/错误ID不残留旧结果，记录过滤不丢草稿，规则与Judge独立，未知值不补零；点击预览/切页零模型调用。新运行必须仍由显式操作发起，真实模型验证另行授权。

总体可行性高：Environment、Runtime、SQLite和已有Trace/证据/图表组件可复用。难点为导航迁移中的状态归属、完整记录列表接口、实时订阅生命周期和旧链接兼容，不是更换UI框架。当前无工时或上线日期承诺，完整功能回归需在实施后重新实跑。
