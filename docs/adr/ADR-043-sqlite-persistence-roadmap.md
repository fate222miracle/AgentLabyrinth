## 目标和现状

当前 Episode、完整 Trace、Checkpoint、Experiment 计划/结果、Job 和 Review 分散在本机 JSON。单文件原子替换不提供跨文件事务，历史和恢复列表需要目录扫描；某些损坏记录会使恢复列表整体不可用。当前已实现来源核验、未知用量保护、失败留存、损坏结果禁止覆盖和评审不完整提示，这些行为必须保持。现有单机单进程、最多两个 Experiment 执行槽是明确边界，不承诺外部写工具恰好一次。

本项目必须让长期实验可追溯、可靠恢复、查询和备份，并支撑后续可复现研究。数据库是工程基础，不直接证明 Agent 正确率、研究创新或多 Agent 协作收益。需求§16将 SQLAlchemy 2.0、Alembic、SQLite 列为技术基线；当前运行代码仍以文件为主，不将历史验收描述为已实现数据库。实施前核对实际依赖和锁文件，新增或更新依赖的版本与范围需明确，不静默更改。

## 候选方案与建议

| 方案 | 收益 | 限制 | 建议 |
|---|---|---|---|
| 继续纯 JSON | 易调试、现有演示可用 | 跨文件一致性与索引受限 | 保留现有回滚与导出路径 |
| SQLite 本地单库 | 事务、索引、部署简单 | 同时只有一个写者；不自动解决外部副作用和多机调度 | 下一阶段首选候选，先隔离验证 |
| PostgreSQL | 面向更高并发和服务部署 | 要有服务运维与迁移成本 | 仅当SQLite形成可测量瓶颈，再按需求§16评估 |

SQLite WAL支持读写并行但仍为单写者，且不适合在网络文件系统上跨机器共享；初期只支持本机单进程调度。[SQLite WAL](https://sqlite.org/wal.html)。每个连接明确启用外键、配置有限 busy timeout；候选 `synchronous=FULL`，以安全优先，实际延迟须测量。SQLite文档指出 WAL 下 NORMAL 在系统崩溃或断电时可能丢失最近已提交事务。[SQLite PRAGMA](https://www.sqlite.org/pragma.html)。这些配置不是断电实测结论，也不能替代备份。

## 数据与事务边界

初版不提前建设用户、多 Agent 或任意知识库。已实施的单 Episode 表保留 UUID、状态、完整版本化载荷、SHA-256、Fake 场景和更新时间；Checkpoint 内含匹配的完整 Trace，完成时原子转换为最终 Episode。原 UUID、schema_version、RunConfig/Agent/Task 来源、Trace 顺序、未知 Token/费用语义不变。

| 对象 | 建议持有 | 关系和约束 |
|---|---|---|
| Episode | ID、状态、来源/时间、版本化完整原始载荷 | 结束结果不可覆盖；历史按ID查找 |
| Trace | Episode ID、事件顺序/ID、版本化事件内容 | `(episode_id, sequence)`和事件ID唯一；保留原顺序和引用 |
| Episode Checkpoint | Episode ID、版本、完整安全点 | 状态和对应已持久化Trace必须在同一事务内协调 |
| Experiment及固定计划 | ID、冻结配置、版本和原始载荷 | 保留配对关系与原计划；未完成不是失败 |
| Experiment成员/Job | Experiment ID、臂/矩阵位置、Episode ID；Job状态/动作 | 一次状态转移仅对实际相关记录使用短事务，不夸大为整场实验一个事务 |
| Review | ID、Episode ID、来源哈希、评审内容 | 独立保存；不改原规则评分；损坏或孤立记录须报告 |

上述是逻辑关系，并不决定把Trace拆表作为唯一权威还是将完整Episode JSON作为权威。优先原始载荷单一权威、索引为可重建投影；如拆表须验证事件完整性、大小、序列和旧Replay一致性。文件原始字节SHA-256与现有模型对象的规范化content_hash含义不同，分别保存、核验，不互相替代。旧版本、无计划、孤立记录和损坏文件不能为了满足外键而伪造父对象，迁移报告应区分未导入及其原因。

本地任务的事务候选：接受Job时原子保存计划与初始状态；Checkpoint与其所需历史协调保存；结束时原子保存结果与同库安全点状态转换；完成Experiment时原子提交汇总和相关Job状态。模型与工具调用发生在事务外，不能持有数据库事务等待网络，调用中断后的未知结果按现有规则保留。外部写工具仍需服务端幂等/去重协议。

## 分阶段路线与验收

**0. 保护与基线**：冻结当前工作树和依赖状态；只读盘点各类文件数量、版本、来源、尺寸和损坏/孤立情况，保存内容哈希清单，不输出敏感正文。选择真实历史的副本和独立Fake夹具，先备份并测试恢复；不读取或发送密钥、不改源文件。建立回放/评分/CSV/失败/恢复的基准快照；测试历史不足时如实记录。

**1. 隔离最小验证**：在全新临时SQLite库建立最小表及迁移版本，先用Fake完成单Episode保存、重启回读、Trace顺序与评分不变；验证事务回滚、重复ID、损坏内容、并发读写和备份恢复。不接正常Web入口、不对历史写入、不接真实模型；通过只是机制验证，不是成品。

**2. 现有功能成品闭环**：按获确认的具体实现方案接单Episode及其Checkpoint/恢复，再接Experiment计划/Job/两侧结果、Review与只读查询；每个切片包括API、Web、CLI、历史查询、明确异常、测试和交接。原则是一次运行只有一个权威存储，不能数据库与JSON独立双写后假称一致；必要时通过可重建导出或明确的迁移步骤提供JSON。保留当前预算、安全点、失败和来源校验，不改变协议/评分或隐式运行。

**3. 非破坏性历史迁移**：停写或在受控静态快照下只读清点→完整备份与恢复演练→导入隔离库→逐文件身份/版本/来源/两类哈希验证→回读核对→报告损坏/重复/孤立/未知→重复导入验证幂等。全量结果与关键样本的Trace、评分、CSV、进度、状态对照；不通过则不切换，不删除或重写源文件。用户确认具体切换及备份后，单一权威从JSON切到数据库；明确切换时刻，避免两边写入。

**4. 验收与观测**：固定Fake多任务集对比旧/新：结果、状态、引用、Trace顺序、预算/费用未知、导出和来源逐项等价；注入进程中断、事务提交失败、数据库锁/满盘/只读、重复请求、损坏和缺失父记录，验证无虚假成功、不覆盖、可定位及恢复。浏览器检查刷新/前进后退只GET、历史草稿隔离、部分错误提示。性能用固定生成数据分别测试1千/1万条记录的历史列表和回读，记录设备、样本、p50/p95及数据库大小；仅作为建议测试规模，目标阈值按实测和课堂需求确定，不虚构提升。

**5. 备份与回滚**：运行中的WAL数据库不能只复制主db文件作为完整备份；采用SQLite在线备份能力或可靠停机快照，实际恢复验证完整性和源哈希。[SQLite备份API](https://www.sqlite.org/backup.html)。切换前明确回滚点、写入冻结、备份和新旧增量导出策略。切换后若已有新数据，不得直接切回旧JSON而丢失期间新增结果；先停写、保存数据库备份、验证增量导出和一致性，再由负责人确认回滚。不要自动清理原始文件。
