# V0.2 收尾与 V0.3 推进复核

日期：2026-10-08。依据：唯一需求 `docs/product/requirements.md` V0.6、AGENTS、Accepted ADR-015–024。代码基线 `4581ffb`，包含当前未提交的课堂 UI 优化；不覆盖既有改动。

负责人本轮要求检查版本完成情况与可推进内容。本轮交付分析、专项验证与交接，没有改业务代码、契约或需求，没有启动整版 V0.3、提交或推送。

## 1. 结论

**V0.2 主要受控能力已实现，但不能标为完整开发和整版验收通过。** 最明确的代码缺口是 FR-08 的跨 Episode 全局 Token 预算；最终真实模型入口和实际交付验收也未收口。

**V0.3 已完成上下文管理首切片，适合继续扩展其网页对照入口与任务长度。** ADR-023 是 V0.2 尚未整版签收时的受控例外，不代表授权同时开发全部 V0.3。API/Schema/对照轴变化须先新 ADR。

## 2. V0.2 对照 §19

| 工作 | 当前实现 | 限制或待验 |
| --- | --- | --- |
| 并发 Experiment、暂停/取消、失败重跑 | 单进程最多两个 Job，第三个排队；冻结计划先于受理；失败重跑使用新 ID | 暂停/取消在 Episode 边界生效；真实模型并发、多 worker 未验收 |
| Checkpoint/Resume | ToolLab、BFCL Python/Java、只读 MCP 单 Episode 与 Experiment 计划恢复 | 已完成产物/安全点校验来源；模型或只读请求中途可能重发 |
| 幂等性 | 已提交安全点与结果复用、身份校验、孤儿状态处理 | 不保证外部写工具恰好执行一次 |
| 全局费用上限 | 独立原厂标价参考预算与网关费用分开记录 | 参考预算是 Episode 准入检查，在途执行可超过预算；网关实付未知时无法宣称实际账单硬上限 |
| 扩展故障注入 | 参数错误、超时、空结果、MCP 断线等固定场景 | 不等于通用任意故障编排 |
| 外部 Benchmark Adapter | 固定 BFCL Python 8 题、Java 5 题 | 本地改编评分，不是官方 BFCL 分数；第二语言来源不是第二个独立 Benchmark 家族 |
| 自动回归 | 四套固定 Fake 套件，配置漂移预检查，失败格报告 | 不代表真实模型批量回归或定时调度服务 |
| LangGraph 与 Runtime 对照 | 独立 StateGraph 调度，与手写调度共享 Session/工具/预算/评分 | 同 Suite 单变量对照；不从短题或 Fake 推导框架普遍优劣 |
| Trace/指标看板 | 单次 SSE、三种回放、成对表、兼容历史最近两次差值 | 对照 Job 没有逐事件 SSE；这不是本次认定的 V0.2 必须缺口 |

Episode 总时限已实现；MCP 可视化、BFCL 回放也已存在，不重复沿用实现前的缺失描述。10 月 8 日 UI 已补结果优先、当前帧参数/反馈/证据、模型等待阶段、三视图共享事件位置；`source-map-js` 安全补丁已完成，前轮 audit 零漏洞。10 月 7 日报告保留为历史快照，其上述待修项不再作为当前缺口。

### 真正需要收尾的工作

1. **全局 Token：代码缺口。** `CreateExperimentRequest.token_budget` 经 `service._with_token_budget` / `_agent_with_token_budget` 应用到每个 Episode；`experiment.py` 只有参考费用的跨 Episode 准入检查。需求 FR-08 要求全局 Token，10 月 1 日任务卡明确延期，目前没有补齐。先 ADR 区分新全局值与旧单次值，定义完成侧、安全点、失败尝试、未知 usage、恢复累计与部分 Pair；明确是边界停止还是可保证的硬预算，不能改标签冒充实现。
2. **真实模型入口：课程运行风险。** 当前配置默认 MiniMax M2.7，Provider 独立默认 GLM 5.3；历史交接还记录过 Key 范围与 MiniMax 不匹配。应统一最终课程选择并用当前账号验证一个模型，保留显式 Fake 备用。目录可见、历史成功和今天实际可调用是不同证据；本轮没有调用真实模型。
3. **交付验收：未签收。** 第二电脑启动、现场流程、实际 200% 缩放/系统减少动效与负责人整版签收仍需实际记录。远端 GitHub/Chromium CI 本轮未查证；本机 Edge 自动测试不能替代它们。
4. **文档与性能声明：待核准。** §16 原规划的数据库/前端库与当前 JSON 原子产物、原生 URL/fetch/CSS 应明确区分；不要为凑技术栈补依赖。单步调度排除模型等待的 <100ms 目标尚无本轮测量证据，需要正式声明达标时补基准。

网关未知费用是需求允许的条件限制，不能靠补零解决；数据库、多 worker、另一 Benchmark 家族不作为当前受控 V0.2 的自动新增任务。

## 4. 建议实施顺序

1. **先补 V0.2 全局 Token 的 ADR 与最小实现，收口一个课程真实模型。** 保留旧字段、历史配置和恢复含义，固定 Fake 回归证明预算边界；现场签收另记。
2. **V0.3 下一最小任务：上下文对照 API/Web。** 复用现有计划、Job、成对结果与流程图，只改变 context_policy；固定 Runtime/模型/工具/任务/Seed/预算。新 ADR 明确轴、版本、恢复和历史兼容，新增失败测试保护来源与单变量。
3. **补少量长链文档任务。** 任务须多步依赖、有中间证据与干扰、确定性目标与评分；原 12 题和旧哈希保留，新增版本化任务。先做少量可解释任务，不急着导入需要复杂外部环境的大套件。
4. **小样本真实对照。** 完成入口后先一个当前可用模型、两题、两种策略、一次 Repeat，共四次 Episode；额外模型请求数量受任务步数/配额约束。记录实际 usage、成功、终止与代价；这个样本只能检查可行性，不能证明统计显著收益。
5. **按失败结果选择 Planning / Memory / Reflection 的一个机制。** 每次先问题与假设，再任务、基线、单变量和指标。第二框架与 LLM Judge 留到明确需要它们的实验，不影响近期课程展示。

展示重点可以是“完整历史和模型实际可见信息为何不同”“哪一步丢失证据、产生重复搜索”“正确率和输入量是否同时改善”。现有当前帧与 MCP 流程展示可直接复用，不另建工作流编辑器、数据库或新画布依赖。
