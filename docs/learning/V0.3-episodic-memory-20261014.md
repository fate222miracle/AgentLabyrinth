## 解决的问题

最近一轮窗口会丢掉旧搜索或阅读结果。单Episode工具记忆将窗口外已经成功返回的完整工具数据带回当前请求，带源call_id并限制UTF-8字节大小。它不是LLM摘要、知识库、持久记忆或新的阅读权限；过大的结果整条跳过，仍可能遗忘失败或增加输入量。

## 阅读顺序

1. `packages/domain/models.py`：ContextPolicy子版本1.1、算法/预算组合校验、旧序列化保持。
2. `packages/runtime/context.py`：完整协议验证→窗口划分→从旧成功反馈选择整条结果→只改投影观察。完整历史不变。
3. `packages/runtime/session.py`：成功工具才追加result，参数错误追加error；请求投影后的字节诊断和原有预算/时间检查。
4. `packages/providers/fake.py`：只解释Provider公开收到的记忆数据，沿用搜索/正文规则；不读取环境私有目标或按Task ID写答案。
5. `packages/application/checkpoint.py`与`experiment.py`：保存完整会话，按原策略和哈希恢复；新策略进入现有配置与对照指纹。
6. `apps/web/src/apiContracts.ts`→`ContextSettings.tsx`→`App.tsx`：子版本验证、单次/右侧配置、CSV保留算法和记忆限额。`EpisodeSummary.tsx`和`McpFlowReplay.tsx`仅显示保存配置/当前事件诊断。
7. `tests/unit/test_context_projection.py`、`tests/integration/test_context_management.py`、`test_context_comparison_web.py`和`e2e/episodicMemory.spec.ts`：大小、来源、失败、恢复和历史草稿边界。

## 调用链与状态

Web显式选择策略→现有创建Episode/API→AgentSpec保存ContextPolicy→Runtime调用Session→project_context验证全部历史→保留最近N轮→选择窗口外成功结果→把记忆数据放入投影后的初始user观察→MODEL_REQUESTED记忆计数/字节/call来源→Provider→实际工具校验/执行→完整历史追加与安全点保存。

记忆每次从完整历史重新生成，不另建可变存储。一个搜索/一个阅读后，完整历史6条消息；窗口1仍只发4条消息，但初始观察包含搜索结果记忆。消息数没增加不等于输入Token不增加，诊断字节会计入记忆内容。恢复后从相同历史得到相同投影，既有成功调用不重新执行。

## 正常、失败与边界

- schema1.0添加memory预算、新算法缺预算、full启用memory、非整数/越界预算都拒绝；旧策略哈希不变。
- 全历史孤儿反馈/重复Call ID/未完成轮次仍在裁剪前拒绝，不通过记忆绕过。
- error反馈、失败/未返回调用不进入；无result结构的其他环境反馈不猜测。
- 记忆数据包按紧凑JSON精确计算UTF-8字节。从最新开始准入，输出恢复原顺序；保留冲突的实际返回，不伪造“正确事实”。超大返回整条跳过，诊断显示省略条数。
- 原始user观察占用保留字段_agentlabyrinth_memory则失败，不覆盖或信任预先植入的假记忆。
- 记忆不修改已获取证据集合；Evaluator继续检查实际工具成功事件，不能仅靠记忆或最终提交获得未读证据。
- 新配置进入安全点身份和实验指纹；窗口无记忆与有记忆不混入同配置趋势。修改草稿不改变历史配置，刷新只GET。
- full vs窗口+memory比较的是整个上下文策略，不能单独归因记忆；固定同窗口开关的消融由下方命令验证。

## 实际验证

初轮49项上下文/恢复验证通过（包含旧24格消融、两种Runtime跨进程恢复与记忆版本/来源/大小验证）。初次运行有沙箱临时目录拒绝及2个旧测试误期望记忆增加消息条数；改为实际4条消息并使用本机测试权限后通过。完整门禁与新增浏览器/跨文档结果完成后记录到任务卡和current-state，不提前宣称通过。

6格初轮Fake结果：两Runtime的full均3模型/3工具通过，window1均6模型/5工具MAX_STEPS失败，window1+memory均3模型/3工具通过；Fake固定Token不代表真实节省。没有运行真实模型，不据此声称真实成功率提升或持续可用。

最终验证：pytest372、mypy102、四套22格回归零退化、旧24格上下文、Web类型/构建/Node37、audit0漏洞；修正旧Trace入口标签及新测试的未来节点假设后完整Edge44/44通过，三场景/两Runtime记忆及API/指纹专项22项通过。详细命令、初次失败和产物目录见任务卡。六格最终报告在artifacts/episodic-memory/d37e3ebf-b79f-4867-98fb-29ccae3abe3a/；累计序列化消息字节full2984、window1为5562、memory2883，最后请求记忆279字节。不是HTTP包或真实Token测量。

## 学习检查与未做

真实小样本进一步验证：窗口1一侧成功读ENTRY/POLICY/DECISION后重复整条链，再提交完整引用（8次工具）；窗口1+8192字节记忆只读一遍（5次工具），两侧评分均通过。总报告Token15766→10317、95849→65122ms；最后模型请求中memory3条/1141字节，近期DECISION之外旧搜索与ENTRY/POLICY可见。固定顺序、有模型随机性与网络波动，不是成功率提升或稳定因果证明，不把这个比例直接写作简历普遍提升。

复现真实小样本：`uv --cache-dir .uv-cache run --locked python -m scripts.episodic_memory_ablation --model coding-minimax-m2.7-free`。只改变记忆开关，仍正式工具/权限/预算/评测；报告退出0仅表示两侧完整运行与保存，结果可能失败，要查看success/reason。Provider失败保留部分报告并停止。CLI run_window_pair先核对保存产物和固定变量，再从成功返回正文计算已读列表；不依赖私有goal_conditions计读。报告目录不能覆盖，默认新UUID。

网页调用链：当前已收到events→flowFrames.documentEvidence→每份资料readCount→DocumentEvidence显示总次数/重复次数。读取开始不累计；TOOL_SUCCEEDED且返回document_id匹配才累计，空document:null仍未取得正文。同一ID再次成功返回计重复；观察者点击、最终快照或引用列表不算阅读。记忆来源call_id与证据取得仍有不同职责，不能靠页面计数伪造评分。

应能解释：为什么必须先验证全历史？为什么4条消息仍能包含搜索和阅读？记忆的来源与工具真正成功有什么关系？大结果为何不截断？消息字节和Token为何不同？同窗口消融为何比full对照更能解释记忆作用？恢复怎样重建而不执行旧工具？

尚未实现跨Episode检索、记忆压缩/淘汰语义、向量库、自动策略选择、LLM摘要、第二框架或多Agent。当前有限字节容量是显式产品边界；是否加入摘要或更复杂检索应由实际失败和新ADR决定。
