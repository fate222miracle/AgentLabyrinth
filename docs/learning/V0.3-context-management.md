## 问题与结论

Runtime 原来把完整历史反复送给 Provider。本切片实现“仅发最近 N 轮完整工具交互”，同时完整保留初始任务、系统指令、Trace 和 Checkpoint。窗口缩小可以减少单次可见内容，但遗忘依赖后反复调用，累计输入可能更大。先用已有原生任务做机制实验，避免为了引框架而引框架。

Fake 决策不是学习模型：文档分支先寻找搜索结果，再检查读到的文档。窗口1忘掉搜索结果后重新搜索，下一轮又忘掉读取结果。这里测的是实现与遗忘机制，不能据此判定真实模型能力或最佳窗口；没有真实 tokenizer、摘要、跨任务记忆或新增模型调用。

## 阅读顺序

1. `packages/domain/models.py`：ContextPolicy、AgentSpec 的版本/校验/兼容序列化。理解“请求投影”与“保存完整历史”不同。
2. `packages/runtime/context.py`：从前缀和完整工具轮次构造 detached projection；全文校验后才裁剪。
3. `packages/runtime/session.py`：observe → call_model → validate → execute；只替换 Provider 入参，不截断 Session.messages。
4. `packages/runtime/handwritten/runtime.py` 与 `packages/runtime/langgraph/adapter.py`：两个调度器共享上述原子行为，无需各写一套窗口算法。
5. `packages/application/checkpoint.py`、`runner.py`：Agent 哈希/完整历史安全点/恢复、只读评分及唯一终态。
6. `packages/providers/fake.py` 的 `_document_response`、`benchmarks/tool_lab_core/tasks/order-status-007.json`：为什么窗口1会失败，而窗口2成功。
7. `scripts/context_ablation.py`：固定矩阵、仅变策略、实际 Artifact 与版本化诊断报告。`packages/application/experiment.py` 固定既有对照的 context_policy，防止混合变量。
8. `tests/unit/test_context_projection.py`、`tests/integration/test_context_management.py`：非法配置、协议、复制隔离、独立进程退出/恢复与单变量检查。
9. Web `apiContracts.ts` → `App.tsx` 与 `e2e/acceptance.spec.ts`：读取和显示新策略；还没有配置新实验的页面入口。

## 调用链与生命周期

```text
CLI load_inputs → 固定 Agent/Task/Seed/RunConfig
  → run_episode → create_runtime → EpisodeSession.observe
  → call_model → project_context(完整历史, ContextPolicy)
  → MODEL_REQUESTED(context诊断) → Provider.generate(投影深拷贝)
  → usage累计 → validate → Executor/Environment.step
  → 追加完整 assistant/tool 轮次 → 安全点 → 下一次投影
  → 停止 → 独立 Evaluator → 唯一 EPISODE_FINISHED
  → Episode Artifact → ContextReport
```

ContextPolicy 随 Agent 固定，进入现有配置哈希；Projection 每次请求临时生成。Session.messages 永远追加，最近窗口只影响 Provider 看见什么。Checkpoint 保存原始完整历史、计数、已执行 Call ID 和策略；恢复用相同规则重新投影，不重复提交过的工具，也不重置预算。

一轮是一个 assistant 的 Tool Call 组及全部对应 tool 反馈，可以包含多个 Call；必须整体保留。当前生产 Runtime 每次只提议一个工具；算法仍验证组内全部 Call、允许对应反馈顺序不同。初始 system/user 前缀全部保留；本切片只接受 Runtime 当前生成的“前缀 + 完整工具轮次”，不支持中途插入 user 或自由 assistant 对话。反馈包括参数纠错反馈，结构规则一致。

状态示例：开始2消息 → 搜索后4消息 → 读取后6消息。第三次请求 full/窗口2发送6消息；窗口1发送初始2消息加最近读取轮次，共4消息。Checkpoint 此时仍存6消息。窗口1随后循环，至第6次模型提议被 `max_tool_calls_reached` 拦住：终止枚举沿用 MAX_STEPS，实际执行工具5次，模型6次，不能把提议算成工具执行。

## 失败与兼容边界

- 字符串/布尔窗口、0/101、full携窗口、近期策略缺窗口、未知算法或额外字段：Pydantic 在调用前拒绝。
- 显式 context_policy 必须 AgentSpec 1.2。旧1.0/1.1及默认1.1无此字段；序列化剔除None，原始配置哈希和22个旧回归单元保持一致。
- 孤儿反馈、重复 Call ID、未完成调用、中途错误角色：先检查完整历史，即使坏轮次将被丢弃也拒绝；Session 以 RUNTIME_ERROR / invalid_context_history 停止，未增加模型调用或产生 MODEL_REQUESTED。
- 窗口丢失证据：不静默退回 full、不自动增加预算，按原预算停止，Evaluator 不把“工具提交过”当成任务成功。
- Checkpoint 策略篡改：Agent 哈希不匹配，拒绝恢复。安全点包含完整历史和累计用量；Provider 正在请求时退出可能重发，这仍不是上游调用恰好一次保证。
- Provider 收到深拷贝，修改嵌套观察不会改写完整历史。工具 Schema 和请求包装不计入字节诊断。
- 字节指标来自 UTF-8 编码的紧凑排序 JSON（ensure_ascii=False），与 Provider tokenizer 或完整HTTP包大小不同。Fake的40/20 Token每调用保持原样；不得用字节推算真实费用。
- 报告是 `fake-context-ablation-v1` 诊断输出，不是新增 Experiment Schema，不进入跨实验趋势或官方 Benchmark 分数。输出目录存在即拒绝覆盖。

## 实际结果（2026-10-04）

两种 Runtime、Seed1/17结果一致；24 Episode，20成功，4个窗口1文档失败符合预期，不把它们标为成功。每题单次运行：

| 原生任务 | 策略 | 独立评分 | 模型/工具次数 | 模拟输入/输出Token | 累计消息字节 |
|---|---|---|---|---|---|
| 001订单 | full / 窗口1 / 窗口2 | 成功 | 2 / 2 | 80 / 40 | 1608 |
| 007文档 | full | 成功 | 3 / 3 | 120 / 60 | 2984 |
| 007文档 | 窗口1 | 失败，MAX_STEPS | 6 / 5 | 240 / 120 | 5562 |
| 007文档 | 窗口2 | 成功 | 3 / 3 | 120 / 60 | 2984 |

当前短链任务窗口2未产生输入节省；窗口1反而令文档累计输入增加约86.4%。这说明不能仅凭“发得短”判定优化有效。未来需有更长、真实模型可解的固定任务和重复小样本，才研究成本收益。

首轮新增测试为29通过、2失败，失败原因是断言把模型第6次提议误计为第6次执行；已按工具预算5纠正并完整重跑。新增浏览器专项首轮6通过1失败，是测试误期望评分徽标写MAX_STEPS；实际页面分别显示FAILED评分与MAX_STEPS终止，已核对截图并纠正断言。阅读指南预览入口原只接受demo-index，已补验证ContextReport后复用同一Fake预览服务，未扩大真实模型或网络权限。
