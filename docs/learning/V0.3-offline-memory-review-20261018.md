# 离线记忆诊断：使用、源码与失败路径

依据需求V0.6及ADR-030/031；对应[下一步计划A](../tasks/V0.3-next-development-20261018.md)。这是已保存记录的诊断工具，不是新Experiment协议、评分、记忆算法或真实模型执行器。

## 解决的问题

把已保存配置、每次请求的窗口/记忆容量诊断、实际成功读取与最终评分放在同一份报告。用户可以沿事件ID核查某条记忆先前是否实际返回，以及再次阅读发生在哪里。报告不能证明因果关系、稳定收益或原文件来自可信第三方；配置哈希和Trace链只是本地一致性检查。

输出：新目录里的`memory-review.md`（阅读表格）和`memory-review.json`（配置、预算、逐次来源与阅读事件）。输入文件保持原样；目录已存在时拒绝覆盖。

## 使用

在仓库根执行，先看无需Key或联网的帮助：

```powershell
uv --cache-dir .uv-cache run --locked python -m scripts.review_memory --help
```

正式Experiment：将下列UUID替换为自己已有的ID。输入目录应直接包含Episode JSON和`experiments/`；可指向隔离测试产物目录，不依赖正在运行的API。

```powershell
$savedExperimentId = '替换为已保存的Experiment UUID'
uv --cache-dir .uv-cache run --locked python -m scripts.review_memory --artifacts-dir artifacts --experiment $savedExperimentId
```

两个独立Episode（按左、右顺序）：

```powershell
$leftEpisodeId = '替换为左侧Episode UUID'
$rightEpisodeId = '替换为右侧Episode UUID'
uv --cache-dir .uv-cache run --locked python -m scripts.review_memory --artifacts-dir artifacts --episodes $leftEpisodeId $rightEpisodeId
```

默认输出`artifacts/memory-reviews/<新UUID>/`；可用`--output`指定一个尚不存在的目录。两个模式互斥。命令成功退出0，输入缺失/校验失败退出2并写拒绝报告；UUID格式错误或输出目录不可创建时，不伪造报告。

没有保存产物的电脑可先运行既有Fake命令`python -m scripts.episodic_memory_ablation`，从其新目录`memory-ablation.json`选择同Runtime的window和memory两个Episode ID，再指定该目录审查；这会生成Fake测试数据，不属于真实模型验证。不要传`--model`来做离线报告，报告入口本身也没有联网/重跑选项。

## 阅读顺序与调用链

1. `scripts/review_memory.py::main`：解析UUID及输入/输出目录，二选一模式；不创建EpisodeService或Runtime实例。
2. `review_memory`：独占创建新报告目录；选择正式配对或独立Episode探索，捕获输入失败并保留拒绝报告。
3. `_read_episode`：Domain的严格JSON解析 → 绑定所请求ID → 原`content_hash`核对Agent/Task/RunConfig；若另有安全点，复用CheckpointStore读取/校验并检查配置冲突。
4. `_experiment_pairs`：`read_experiment`和`fixed_config`检查版本/配置哈希；校验配对所有权、完整Task×Seed×Repeat矩阵。原`_validate_memory_agents`/`_validate_context_agents`负责固定变量；逐侧绑定保存臂配置、任务、环境/Seed及结果用量；冻结计划仍在时复用其`verify`并检查来源。
5. `_complete_trace`：复用JsonTraceRecorder检查已保存前缀的身份/链；完整记录再核对终止、步数、模型/工具计数和已报告用量。没有完整起止记录时阅读数为未知，不补零。
6. `_request_rows`：按事件顺序建立“提议→成功返回”索引；每次MODEL_REQUESTED只可引用此前已成功返回的call_id。核对保存策略、整数计数、消息数量、记忆预算/来源数量，不从未来事件补来源。
7. `successful_document_reads`：共享给原`episodic_memory_ablation.run_window_pair`，仍使用实际成功返回且document_id匹配的口径；按时间扫描修正原CLI先收集全体提议可能关联未来事件的隐患。没有新增Provider或工具调用，原报告字段保持。
8. `_episode_row` → `_markdown` → `write_text_atomically`：只投影配置/计数/来源ID，不导出私有目标、文档正文、隐藏思维链或原始校验异常。JSON是独立诊断报告，不作为Episode或Experiment回读。

## 如何解读

- `memory_sources`绑定proposal_event_id、return_event_id及实际call_id，能回到保存Trace核对。这里只核对“此前成功返回的来源”，不宣称重新构建了全部模型输入或复现了Provider tokenizer。
- `memory_omitted_entries_count`是保存的跳过条数。当前Trace没有逐条跳过来源清单，报告明确不猜测；也不因跳过和失败同时出现就宣布因果关系。
- 无记忆策略缺少记忆诊断字段保持未记录；整段诊断缺失与存在但损坏区分，前者未知，后者拒绝。不擅自恢复到full或重新调用模型补信息。
- `reported_usage`只保留供应商已报告的部分。请求没有对应响应或记录`upstream_usage_unknown`时`usage_complete=false`，零值不能解释成零消费。Fake用量单独保留`simulated`标记。
- 重复读取等于同一Episode中同一document_id首次之后的成功读取次数；参数错误、失败、空返回、未执行提议和观察者预览不计。不判定重复一定无效，也不以少读但任务失败当优化收益。
- 两个独立Episode始终标探索；不会给旧CLI样本补Experiment ID或作为新正式实验。
