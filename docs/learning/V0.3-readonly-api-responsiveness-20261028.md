## 问题与范围

Episode/Experiment/Review详情与看板已在API层把同步读取交给线程；但恢复列表和Job轮询还有四处直接在async路由中扫描/解析文件。目录大或读盘慢时，事件循环被占用，元数据和其它请求也无法及时响应。

只修改`apps/api/main.py`四个GET的读取位置，复用现有`asyncio.to_thread`：

- `/api/v1/episodes/resumable`
- `/api/v1/experiments/resumable`
- `/api/v1/experiments/jobs/resumable`
- `/api/v1/experiments/jobs/{id}`

服务层仍是同步只读函数，CLI调用方式不变。API响应、错误码、文件验证、排序、评分、CSV和模型权限不变，无新依赖/公开契约，属于现有范围的普通修复，不新增ADR。

## Job快照竞态

移出主循环后，Job可能在文件快照被读取期间完成。仅用返回时的活动字典判断，会把此前真实的running快照误标为interrupted。

路由先记录开始时Job是否活动，再读取。若开始时活动，保留读取到的快照，下一次轮询可显示completed。若两端都不活动且快照queued/running，则额外复核一次文件；状态变化或任务已活动就返回复核结果，仅稳定且仍无活动任务时按原规则标孤儿中断。这样也覆盖任务在整个读区间内启动又结束、两端均不活动的情况。只条件复核一次，不无限轮询；活动字典过滤仍在事件循环，不交给读取线程修改。

这不是数据库事务或线性化的最终状态读取；列表也可能在下一次刷新前过期。真正执行、恢复、暂停和取消仍走原POST校验，不把这些读/写临界段随意拆到线程，避免新增重复调度竞态。没有把所有同步I/O都宣称已解决。
