范围由负责人在 2026-10-22 明确授权：**一个模型、一道题、左右两侧各一次**，跑完即止。不是批量、不是 Seed×Repeat、不构成成功率或收益结论。

## 1. 结论

- 真实模型 `coding-minimax-m2.7-free` 在原生题 `order-status-001` 上，**左右两臂都 SUCCESS**，Step 2/2、Token 2790、模型调用 2、工具调用 2，报告用量与费用两侧完全一致。
- 右臂真实走通第三 Runtime：`runtime_version = pydantic-ai-slim-2.57.0`，左臂 `reference-v2`；保存的实验是 `ExperimentArtifact 1.7`，配置里两臂 backend 分别为 `handwritten` / `pydantic_ai`。
- 两侧 Trace 事件序列逐项相同，均为 17 个事件（`EPISODE_STARTED`→两次 `MODEL_REQUESTED/RESPONDED`+`TOOL_*`→`EPISODE_FINISHED`），**没有出现框架额外的模型请求**，说明桥接层“一次框架模型请求＝一次 `Session.call_model()`”在真实 Provider 下成立。
- 这仍是**单对样本**：只证明该模型该题当前可用、第三调度链路真实接通，不证明 PydanticAI 相对 Reference 有收益、延迟差异有统计意义或长期可用。

## 3. 调用链（右臂实际路径）

1. `apps/api/schemas.CreateExperimentRequest(schema_version="1.10", comparison_axis="runtime_backend", runtime_target="pydantic_ai")` → `apps/api/service.EpisodeService.execute_experiment`。
2. `prepare_experiment` 固定计划：左臂 `handwritten`/AgentSpec 1.1，右臂 `pydantic_ai`/AgentSpec 1.4，生成 `ExperimentCheckpoint 1.5` 后落盘。
3. `packages/runtime/factory.create_runtime` 依 backend 返回 `PydanticAIRuntimeAdapter`；`runtime_version("pydantic_ai")` 读实际分发得到 `pydantic-ai-slim-2.57.0`。
4. adapter 循环调 `EpisodeSession.observe/checkpoint`；`node == "model"` 时把 `_SessionBridgeModel` 交给 `Agent.iter`，框架只产出单步内节点（`ModelRequestNode → CallToolsNode → End`）。
5. 桥接 `request()` 内部只调一次 `session.call_model()`，把 Session 已裁决的调用映射为 `ToolCallPart`（工具定义取自 `session.available_tools()`），用量不采信框架（`RequestUsage()` 为空，真实用量仍由 Session 记录）。
6. 步间回到 adapter：`node != "model"` 时先 `session.validate()` / `await session.execute()` 再 `checkpoint`，与 Reference 共用同一套校验、预算、Trace 与安全点。

## 4. 状态变化与失败路径（本次未触发，仍须遵守）

- 无新增状态：右臂事件与左臂逐项相同；安全点、Checkpoint、评审输入均走既有版本。
- 失败路径沿用实现期已验证的边界：未注册工具名不产出调用、交回 Session 裁决；框架异常被 adapter 捕获后仍由 `session.validate()` 决定终止原因；缺分发或元数据缺失抛 `RuntimeUnavailable`，**不回落 `handwritten`**、不伪造 `reference-v2`。
- 一次真实调用已消耗额度：本对共 4 次模型请求（两侧各 2 次），无重试、无补跑、无模型替换。
