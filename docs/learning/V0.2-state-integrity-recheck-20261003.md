# V0.2 再次复核：状态、费用与 Job 持久受理

依据唯一需求 V0.6、AGENTS、ADR-014/015/016/019/020，以及本轮 ADR-021。此次是已有 V0.2 能力的可靠性收尾，不是整版签收。辅助 Agent 只读复核，Codex 串行改代码。

## 源码阅读顺序

1. `packages/runtime/handwritten/budget.py` 的 `accrue_usage` → `tests/unit/test_budget_tracker.py` → `tests/contract/test_langgraph_runtime_adapter.py`。先看一次响应怎样完整入账，再看 Token/费用判限。两个 Runtime 共用此规则。
2. `packages/application/experiment.py` 的 `create_experiment_plan`、`run_experiment`、`run_arm` → `tests/integration/test_experiment_resume.py`、`test_reference_budget.py`。计划是固定输入，完成的 Episode 是进度账本；文件存在不等于可复用。
3. `apps/api/service.py` 的 `prepare_experiment`、`reserve_experiment_job`、`execute_experiment`、`_resume_experiment_once` → `apps/api/main.py` 的 Job 创建、调度和控制 → `tests/integration/test_experiment_jobs.py` 与 `_checkpoint_worker.py`。
4. `apps/web/src/requestGeneration.ts` → `App.tsx` 的历史读取、Job 创建/控制和轮询 → `apps/web/tests/requestGeneration.test.mjs`。请求仍可能在服务器执行，但只有当前页面所属的响应可以更新页面。
5. `EpisodeService.get_episode/get_experiment` → 两个历史 GET → `tests/integration/test_history_integrity.py` 与旧产物 fixture。Episode 本轮新增内部 ID 检查；未新增完整 Episode 配置哈希校验。Experiment 沿用原始 config 哈希，兼容 1.0。

## 调用链与状态变化

```text
Web 创建 Job
  → Origin 校验、Pydantic 参数校验
  → prepare_experiment（任务、模型准入、配对 Agent、Seed、预算、配置）
  → create_experiment_plan（固定快照与 plan_hash，Checkpoint 1.0）
  → 计划原子落盘 → queued Job 原子落盘 → 返回 202
  → 调度器等待两个执行槽位之一 → running
  → 从同一计划执行/恢复 → 每侧 run_arm
      → 完整结果：核对 ID、Agent、Task、RunConfig 后直接复用
      → 恢复或新执行：检查参考预算，再读安全点或新建 Episode
  → 保存各 Episode → 聚合 Experiment → completed
```

- 计划不包含 Key。Provider 实例仍按侧创建，恢复时 Fake 的调用计数来自安全点；两个 Runtime 的调度仍独立。
- Token 超限前先累计本次 prompt/completion、已知费用或未知标记，再按 prompt → completion → task Token → cost 的既有优先级确定终止。安全点和最终结果得到相同完整计数。
- 正常暂停/取消仍在 Episode 边界生效。无人执行的 queued/running 孤儿可以显式恢复；无有效计划的旧孤儿只能取消并创建新实验。取消直接写终态，不依赖已退出的执行者。
- Web 页面代际在读取、运行、恢复或导航时更新；旧响应不能设置结果、URL、错误或结束新请求的加载。Job 控制还检查控制请求顺序，避免 pause/cancel 响应倒序。恢复受理时解除旧 Job 观察，受理成功后重新绑定；防止已暂停的观察器留下永久加载状态。
- 历史 GET 在线程中读取，避免慢文件读取占住事件循环。Checkpoint 的同步 fsync 本轮未改为异步，也未实现多进程存储。

## 失败路径和边界

| 触发 | 当前行为 | 证据 |
| --- | --- | --- |
| 模型返回 Token 超限且产生费用 | 记录已产生费用，保留 Token 终止优先级；未知费用不变成已知零 | 三种 Token 超限 × 已知/未知费用、安全点恢复；两 Runtime 最终费用断言 |
| 两 Job 占用执行槽位，第三个排队时进程退出 | 第三个已落盘固定计划，重启显式恢复原 Seed/重复次数 | 子进程实际 `os._exit` 后恢复完成，四个唯一 Episode ID |
| 计划写入失败 | 不返回 202、不保存 Job、不调度、不调用模型 | 写入故障注入 |
| 计划已写，Job 状态写失败 | 不返回 202；重启可经非 Job 计划恢复入口发现有效计划 | 第二次写入故障注入；两文件不是事务 |
| 最终 Episode JSON 损坏，但安全点有效 | 从安全点恢复同 ID，已完成另一侧字节不变 | Experiment 恢复集成测试 |
| 完整 Episode 的内部 ID 或来源不匹配 | 拒绝复用、拒绝作为重跑源；不自动重算掩盖来源错误 | 恢复 foreign-id 与历史身份测试 |
| 参考预算已耗尽，坏文件冒充完成结果 | 不能凭文件存在跳过预算；恢复/新执行前拒绝 | 参考预算与损坏文件组合测试 |
| Job 受理/恢复较晚返回，用户已经离开 | 服务器继续，旧响应不夺回页面 | 请求代际测试、浏览器延迟 8 秒受理后打开历史 |
| failed Job | 不进入“可恢复”列表；提示保留结果并检查后创建新实验 | 与既有后端契约对齐，未放宽失败恢复 |
| Experiment ID、config_hash 或 Pair 数量不符 | 历史详情拒绝并返回统一安全错误；合法旧 1.0 仍可读 | 历史测试，不修改产物字节或调用 Provider |

## 下一步与学习追问

当前已推进“请求归属抽离 + 持久受理统一恢复”这一步架构改进。可继续在 V0.2 内补前端 API 边界运行时校验、Job/历史读取交互自动化及统一自动质量门禁；按需求建立下一张任务卡，不因 App 较大盲目拆空层。

整版仍待最终免费模型选择与最新真实小样本、负责人延期的跨 Episode 全局 Token、真实 200%/Windows 减少动效、第二台机器和现场签收。全局 Token 不是当前 `token_budget` 的已有语义。数据库只在单独 ADR 和授权后实施；本轮没有新增数据库或 V0.3 能力。

建议读源码后追问：为什么 202 必须晚于计划落盘？两次原子写入为何仍不是事务？为什么预算终止不能漏掉最后一次账单？为什么导航失效请求不等于服务器取消？为什么一个完整但 ID 不同的文件比损坏 JSON 更应拒绝自动恢复？
