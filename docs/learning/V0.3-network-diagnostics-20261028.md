# V0.3 网络失败诊断与异常分类修复

日期：2026-10-28；SSOT V0.6。负责人要求先修存量问题；本轮不新增Agent机制、依赖或公开协议。分支codex/fix-provider-network-diagnostics，保护全部先前未提交成果；无Git提交/推送、真实推理、Judge或恢复。

## 1. 已确认的问题与修复

`packages/providers/aihubmix.py`原目录GET和推理POST各自捕获URLError后丢弃reason，仅保留NETWORK_CONNECTION_FAILED。包装在URLError中的TimeoutError也因此误标网络失败；响应读取阶段的ConnectionResetError/IncompleteRead未统一处理。另有HTTP错误正文截断时异常逃出原状态映射的问题。

现在两条路径共用私有`_transport_failure`，按异常类型生成安全的本地分类日志，覆盖建连及读取；包装超时使用已有REQUEST_TIMEOUT，其余传输故障仍使用已有NETWORK_CONNECTION_FAILED。HTTP401/429/5xx与已知供应商代码的原优先级保持；错误正文截断仍保留已经收到的HTTP状态，不被原始读取异常覆盖。

这是Provider内部异常处理修复，没有增加ModelProviderError代码、Domain/Trace/API/CSV字段或新请求入口，故不新增协议ADR。分类只进入后端日志，页面和旧保存记录不自动获得细类；不能把旧368937f4…倒填成DNS、TLS或代理问题。旧Trace字节保持。

## 2. 如何阅读诊断

入口：`list_available_model_ids` / `AIHubMixModelProvider._send_http_request` → `_transport_failure` → 原ModelProviderError处理。Runtime仍保存失败、缺响应时保持未知用量；Experiment仍据既有未知用量保护停止后续准入。Judge复用Provider，但不自动重试。

后端控制台示例（格式示例，不是本轮真实DNS故障）：

```text
provider_network_failure provider=aihubmix operation=completion category=DNS_LOOKUP_FAILED
```

operation为catalog（目录读取）或completion（推理请求），分类含义如下：

| category | 含义与下一步检查 |
| --- | --- |
| DNS_LOOKUP_FAILED | 地址解析失败；检查本机或代理链路的解析配置。 |
| TLS_CERTIFICATE_ERROR | 证书校验失败；检查时钟、受信任证书与代理证书配置，不能关闭校验掩盖问题。 |
| TLS_ERROR | 其它TLS握手/加密连接异常；需核查代理与服务端连接。 |
| REQUEST_TIMEOUT | 建连或读取超时；不能仅凭超时判断请求未执行或未计费。 |
| CONNECTION_REFUSED | 对端拒绝连接；检查代理/目标服务与端口。 |
| CONNECTION_INTERRUPTED | 连接重置、中止、管道断开或HTTP响应未读完整。 |
| HTTP_PROTOCOL_ERROR | HTTP协议或响应状态行异常。 |
| NETWORK_UNREACHABLE | 系统报告网络/主机不可达。 |
| NETWORK_UNKNOWN | 异常类型不足以细分，保留未知，不按异常原文猜测。 |

只输出固定类别与固定operation，标准LogRecord也保留这三个结构化字段。不会记录API Key、代理地址/认证、URL、请求/响应正文、原始reason、堆栈或隐藏推理；不靠原文字符串匹配分类。日志不新增Episode/request_id关联字段，不能冒称已有完整链路追踪；将来若需要公开或持久化细类，先定义具体协议。
