# V0.3 SQLite Experiment / Job / Review 持久化交接（2026-10-30）

依据：requirements V0.6、Accepted ADR-043。负责人要求继续推进 V0.3；本轮不调用真实模型、不迁移旧历史、不提交 Git。

## 交付结果

产品默认 SQLite 现同时保存新单次与成对 Episode、Experiment 冻结计划、最终结果、后台 Job 和独立 Review。Experiment 受理时计划与初始 Job 在一个短事务提交；运行期间不持有事务等待模型或工具；最终结果写入与计划退役在一个事务完成。新记录不再同时写 JSON，旧 JSON 只读回退且同 ID 内容冲突会失败。

迁移 `0002_experiment_records` 增加一张版本化载荷表，保留对象原有 Pydantic 契约和 SHA-256 完整性检查；Review 用 `parent_id` 索引 Episode，Experiment/Job 继续保留原 UUID。SQLite 在线备份入口会自动覆盖新表，无需新增第二套备份代码。

## 源码阅读顺序

1. `packages/infrastructure/migrations/versions/0002_experiment_records.py`：表和不可破坏降级边界。
2. `packages/infrastructure/sqlite_episode_store.py`：短事务、摘要核验、不可覆盖结果、Job 更新和 Review 查询。
3. `packages/application/experiment.py::run_experiment`：注入 Episode/Experiment 存储 Port，配对执行不感知 SQLite 细节。
4. `apps/api/service.py`：数据库优先、旧 JSON 回退、来源冲突和恢复选择。
5. `tests/integration/test_sqlite_episode_product.py`：新进程回读、配对执行、Job 恢复、Review 与无 JSON 双写。

主调用链：

```text
POST Experiment Job
  -> prepare_experiment
  -> reserve_experiment(plan + queued job，同一事务)
  -> run_experiment
  -> paired Episode checkpoints/results（SQLite）
  -> save_experiment_result + retire plan（同一事务）
  -> update completed job
```

旧计划恢复会继续使用旧文件 Episode 存储；数据库计划只使用数据库 Episode 存储，防止在恢复时把两种权威来源混用。页面刷新、Dashboard、进度和 Review 仍是 GET，不触发运行或评审。

## 失败与修复记录

首次完整门禁发现 Dashboard 在遇到 `broken.json` 时于 UUID 集合构造阶段提前抛错，未按原行为保留有效实验并计入损坏数。根因是目录扫描提前从路径构造 UUID；修复为逐文件隔离解析，损坏文件只增加 `skipped_count`。另一次定向回归发现列表先核验了无关 Review 的已丢失 Episode，已恢复“先识别归属、只核验目标 Review 来源”的边界。
